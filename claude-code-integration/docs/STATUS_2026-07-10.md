## 三、已知缺点与不足

### 3.1 Token 追踪缺失 🔴

**这是最大的缺陷。** 在当前架构中，完全无法追踪 token 消耗：

- Claude API 返回的 `usage` (input_tokens / output_tokens) 不暴露给工具层
- Read 工具不返回 token 数
- SparseRead MCP 工具不返回 token 数
- `sro_trace` 返回 `tokens: 0`
- 只能用 tiktoken 离线估算，结果不精确

**影响：**
- 无法向用户展示 SRO 实际省了多少 token
- 无法做 A/B 对比
- 无法优化 Gate 阈值

**可能的解决路径：**
1. 在 SparseRead MCP Server 侧，对每次响应内容用 tiktoken 计数，写入 trace
2. 在 Claude Code Hook 侧，通过 `additionalContext` 注入估算的 token 节省量
3. 长期：等待 Claude Code 暴露 usage API

### 3.2 不能拦截 Grep/Search 工具 🟡

- PreToolUse Hook 只能拦截 `Read` 和 `Bash`
- Claude Code 的 `Grep` / `Glob` / `WebSearch` 等工具不在 matcher 范围内
- 依赖 CLAUDE.md + MCP tool description 软引导

### 3.3 Hook 无状态 🟡

- 每次 PreToolUse Hook 调用启动新进程
- 无法维护跨调用的 Gate 状态
- 无法实现"同一个文件第二次读放行"等策略
- 改为 session 模式 Hook 可解决

### 3.4 Gate 对代码文件的判断 🟡

- `orchestrator.py` 53KB → Gate 判断 `sparse_recommended: false`
- 理由是代码文件直接读更高效
- 但如果是几百行的重构任务，SRO 可能仍然有价值
- 需要根据实际场景调整阈值

### 3.5 SparseRead 无 Skill 注册 🟢

- 不能 `/sro-check` 或 `/sparseread`
- 用户只能口头指令或依赖自动触发
- 可以通过 `.claude/skills/sro/SKILL.md` 轻松补上

### 3.6 Windows 环境兼容性 🟡

- OpenClaw 的 `run_qcb_trusted_batch.sh` 在 Windows 不兼容
- PinchBench 依赖 Linux bash 脚本
- WSL 可规避但增加复杂度

6. **Gate 阈值调优** — 基于实际使用数据调整文件大小阈值和类型判断
